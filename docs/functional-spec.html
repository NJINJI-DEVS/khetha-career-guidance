1. Introduction

1.1 Purpose

This document specifies what Khetha Career Guidance actually does today, for each of its four user roles, as implemented in the codebase. It is written to be read by reviewers, evaluators and new engineers who need an accurate picture of system behaviour without reading the source directly.

1.2 Scope

Covers the React/Vite frontend, the ASP.NET Core backend API, the Supabase-hosted Postgres database and authentication service, and the platform's deployment posture. Excludes internal code style, algorithmic implementation detail beyond what a functional description needs, and any roadmap items that exist only as intentions rather than code.

1.3 How to read this document

Every feature described here was confirmed by reading the relevant source file(s) directly — this is not a description of intended behaviour, product copy, or a pitch deck. Where a feature is incomplete, simulated, or makes a promise the code doesn't keep, it is labelled explicitly with one of these tags, matching the standard used throughout this project's own internal audits:

CONFIRMED fully implemented and backed by real logic/data   PARTIAL implemented but incomplete, simulated, or unenforced in part   GAP a claim made in the product (copy, UI text) that the code does not currently deliver

2. System Overview

2.1 What Khetha is

Khetha is a mobile-first Progressive Web App built for South African learners navigating the transition from Grade 9 subject choice through to Grade 12 university/TVET/funding applications, aligned to DHET's National Career Advice Portal (NCAP). It also serves three supporting roles: verified mentors and industry professionals who assist learners directly, and departmental administrators who approve and oversee that network.

2.2 Technology stack

LayerTechnology
FrontendReact (Vite build), Tailwind-style utility CSS with a custom government colour theme, vite-plugin-pwa for installability/offline shell caching
BackendASP.NET Core 8 Web API, Entity Framework Core (Npgsql provider, snake_case naming convention)
Database & AuthSupabase — managed Postgres, and Supabase Auth for all sign-in methods (the backend never issues its own tokens; it validates Supabase-issued JWTs against Supabase's public key set)

SMSTwilio, as the SMS provider behind Supabase's phone-OTP sign-in (configuration in progress at time of writing)

2.3 Deployment & infrastructure

The frontend deploys via GitHub Actions (FTP to cPanel hosting) on push to main. Two workflow files exist for this (build.yml and deploy-frontend.yml); build.yml duplicates build steps redundantly and appears to be leftover rather than authoritative — GAP this should be confirmed with the team and the stale one retired.

Backend hosting could not be confirmed from the repository. No reference to Azure App Service (or any other host) exists in application configuration, workflow files, or documentation. The repository's own README.md backend section is stale — it describes endpoints as "planned" that have long since been built, under different route names than it lists, and asserts the browser "never talks to Supabase directly," which contradicts the frontend's actual authentication code (it talks to Supabase directly for every sign-in method). Backend hosting details in this document should be verified against the actual hosting platform, not this repository.

3. Roles & Access Control

Four roles exist: STUDENT MENTOR PROFESSIONAL ADMIN. Student, mentor and professional are self-claimable at first sign-in; administrator access is never self-service — it is granted only by an existing administrator, or, for the very first administrator ever, by matching a configured bootstrap email on first sign-in (a path that closes permanently once one admin exists).

CONFIRMED An account is bound to its role permanently. The first successful role claim wins — a repeat claim (even a race between two simultaneous requests) is rejected and simply returns the account's actual role rather than changing it. Mentor and professional roles additionally require passing the verification flow (Section 7.1) before they can act as a mentor; student and admin do not require separate verification.

4. Authentication & Account Lifecycle

Five sign-in methods exist, all via Supabase Auth directly from the browser — the backend is never involved in issuing credentials, only in validating the resulting token:

MethodStatusNotes
Email + passwordCONFIRMEDWorks with zero extra configuration. The only method with an explicit "Sign in / Create account" toggle, because Supabase will not silently create an account from a plain sign-in call the way the other methods do.
Email one-time codeCONFIRMEDPasswordless; auto-creates the account on first use. A crash bug that broke every OTP verification (an uncaptured variable) has been fixed.
Phone (SMS) one-time codePARTIALCode path is fixed and correct; SMS delivery depends on the Twilio configuration being completed and correctly registered for South African carrier delivery (see Section 12).
Google OAuthPARTIALFully wired; will show a clear "not set up yet" error until the Google provider is enabled in the Supabase dashboard and its redirect URLs are correctly allow-listed.
Apple OAuthPARTIALSame status as Google.

Google, Apple and phone sign-in all double as sign-up for a new user with no separate button — Supabase creates the account automatically the first time any of them succeeds. Only email+password needs an explicit choice between signing in and creating an account.

Session persistence: once signed in, a learner stays signed in on the same device/browser indefinitely (Supabase's own long-lived, auto-refreshing session token), and the app restores their role and profile automatically on every reload rather than asking them to sign in again — this only re-triggers if they explicitly sign out, or if the underlying session token itself expires or is revoked.

5. Consent, Privacy & POPIA Compliance

Three consent items are collected at account creation: a mandatory core consent to store a career profile, and two optional consents (reminder notifications; anonymised use for research). A minor's date of birth is captured via a real date picker (not a self-declared age tick-box), and guardianship details — name, relationship, contact number, and an explicit confirmation that the guardian was shown and agreed — are required before a minor's account can proceed.

CONFIRMED Consent is recorded once, server-side, with a version number; a returning user is never re-asked unless the consent wording itself is later versioned up, in which case everyone is asked again. Every consent record write is logged to an audit trail.

CONFIRMED "Export my data" downloads the learner's actual backend record as JSON.

GAP "Delete my results" clears only the learner's saved journey/results data (a single JSON field), not the account itself. The learner's profile row, subjects, consent record, messages, help requests and notifications all remain. This is a genuine improvement over the previous version (which didn't even persist the deletion server-side at all), but it is not a full "right to erasure" and should not be described as one without a companion account-deletion capability.

6. Learner Functional Requirements

6.1 Onboarding & profile setup

Shown once, immediately after a student's first real sign-in. Collects full name, grade (9–12), province, and an optional school name. Grade 10–12 learners additionally enter their current subjects and percentages (with an option to speed this up via the report-card scanner, Section 6.12); Grade 9 learners skip subjects entirely and are pointed to Subject Chooser instead, since they have no NSC marks yet. A short preferences form (interests, career goals, desired education level, province, study mode) is captured at the same time. CONFIRMED All of this is persisted server-side against the learner's account, including grade, school and province as first-class fields rather than derived guesses.

6.2 Dashboard / Home

The landing screen shows the learner's current APS, a count of qualifications they're eligible for, and a 4-step journey completion tracker. It routes Grade 9 learners toward Subject Chooser and Grade 10–12 learners toward the APS Calculator, surfaces up to two unread notifications, and — for Grade 9 specifically — a preview of their top three recommended subject packages. Includes quick links to every major tool, a "browse careers by field" grid with live counts, and a shortcut to the report-card scanner and SMS summary.

6.3 APS Calculator

CONFIRMED APS is computed as the sum of NSC achievement levels (1–7) for the learner's best six non-Life-Orientation subjects, matching the standard national APS methodology. A Maths Pure/Literacy toggle materially changes which qualifications are shown as eligible. A "what-if" slider per subject lets a learner see how a different mark would change their APS and eligibility in real time, with an NSC level-band reference table alongside it.

6.4 Subject Chooser & Subject Evaluation

Subject Chooser (Grade 9→10 decision) is a four-step guided wizard: it explains the decision, lets the learner optionally narrow by interest area, collects Grade 9 marks, and returns a ranked list of the nine subject packages with a plain-language verdict (Strong / Within reach / Stretch), the specific gaps and strengths behind that verdict, and explicit warnings when a Mathematics or Natural Sciences mark puts a whole pathway at risk.

Subject Evaluation is the Grade 10–12 equivalent: instead of choosing a pathway, it shows which single subject-mark improvement would unlock the most additional qualifications ("if you could lift one mark"), near-misses when no single lever helps, and a per-subject breakdown of what each one currently opens or blocks.

6.5 Career Choice & Job Fit questionnaires

CONFIRMED Career Choice is a 12-statement instrument built on the Holland/RIASEC interest model — the same model NCAP's own questionnaire uses — producing a three-letter interest code and a ranked list of matching careers. Job Fit is a 10-statement instrument scoring five work-context preferences (people/data/things/outdoors/routine) and matching them against each occupation's own context profile by distance, producing a percentage fit per career. Both results are saved to the learner's journey and referenced elsewhere in the app (e.g. the Advisor chat is told the learner's interest code as context).

6.7 CV Builder

A six-step guided CV wizard (contact, summary, education, experience, skills, languages/references) with a live completeness score and a single prioritised "fix this next" suggestion. Offers writing help throughout — opener prompts, action-verb lists, a one-click pull of subjects from the learner's own Khetha profile, and skill suggestions drawn from their saved career interests. Produces two applicant-tracking-system-safe templates (deliberately plain, single-column); export is via the browser's print-to-PDF, not an image. CONFIRMED A CV can be shared via a revocable, token-based public link with no login required to view it.

6.8 Mentor Hub (learner side)

A learner can search/filter the verified mentor and professional directory by role and province, and send a help request (goal, subject, and a statement of need) — their APS and marks are attached automatically from their own stored profile, never typed in by hand. Their own request history is visible read-only; they cannot accept or action their own requests. Once a mentor accepts, an in-app chat opens.

6.9 AI Advisor chat

A small set of instant, offline-safe scripted answers is tried first for common questions. Anything else falls through to a real AI-generated answer (Anthropic Claude), scoped by its own system prompt to South African subject/APS/career/funding topics and instructed to redirect anything outside that scope — legal, medical or safety questions — to the human Advice directory instead of answering them. If the AI call fails for any reason (offline, no key configured, network error), the chat degrades to a static helpful message rather than breaking. The chat's own language can be set independently of the rest of the app, across six languages.

6.10 Academic Calendar & Event Invites

The calendar shows South Africa's academic-year holidays, terms, exam windows and application deadlines (with a provisional-dates disclaimer), overlaid with the learner's own accepted mentor sessions. Event Invites lists admin-approved mentor-run seminars, shadowing days, site visits and talks, split into "you're going" and "also on offer," with honest capacity messaging (a slot count is only shown when it's real) and race-safe accept/cancel against the server's live seat count.

6.11 Profile, Settings & Privacy controls

Three tabs: Journey (stats and saved tool results), Saved (favourited careers/qualifications/providers), and Settings — which covers language, the shared preferences form, light/dark/system theme, accessibility (four text-size steps, high contrast, reduced motion, plain-language mode, read-aloud), offline/low-data controls, per-category notification toggles, and the privacy panel (consent toggles, export, delete — see Section 5).

6.12 Offline support & PWA tools

The Offline Centre shows connection status, last-saved time, manual save and per-content-pack offline download, plus a snapshot of everything currently saved on-device. The SMS Summary tool compiles the learner's assessment results, qualifying courses with deadlines, and funding information into a single plain-text message short enough to send over basic SMS, intended to also be forwarded to a parent or guardian.

GAP The report-card scanner is a simulation. It animates a scanning effect and then reveals pre-set example marks — the app is explicit about this in its own on-screen copy ("Optical character recognition is simulated in this build"). No real OCR or image recognition currently runs.

7. Mentor & Professional Functional Requirements

7.1 Verification & onboarding

A three-step application: identity (full name, SA ID/passport, ID document upload), professional context (institution/employer, field, subjects they can help with, a free-text experience claim, work email, optional professional-registration body and licence number, optional partner-organisation code, academic transcript upload), then a review-and-submit summary. The backend independently computes a fraud-risk score on submission and records it for admin review. Only one pending or approved application can exist per account at a time.

On approval, the mentor is granted "verification tiers" reflecting what they actually proved: an ID tier if they uploaded an ID document, a qualification tier if they supplied a transcript or licence number. GAP A third "partner-vetted" tier exists in the data model but is not reachable through the normal application flow — the partner code a mentor submits is deliberately not treated as proof of vetting, and no admin workflow was found that separately grants it. Until one exists, this tier is effectively dead.

7.2 Mentor Workspace

An approved mentor sees stat tiles (awaiting reply, accepted, letters issued), a filterable list of incoming help requests with the learner's stated goal, subject, marks and APS, and Accept/Decline actions — disabled entirely until their application is approved. Accepted requests surface an "issue a recommendation letter" action. The workspace also embeds the mentor's own event-hosting tools (Section 7.5).

7.3 Help requests & messaging

CONFIRMED A learner's APS and marks are snapshotted from their own stored profile server-side at request time — never trusted from the client. A mentor can only respond once per request (accept or decline). Messaging only opens once a request is accepted, and — this was specifically verified as still true and server-enforced, not a deprecated claim — every message body is redacted for sensitive content (e.g. contact details) on the server before it is ever stored, so a modified client cannot bypass it.

7.4 Recommendation letters

A mentor can issue a letter for an accepted request, choosing a strength (strong / qualified / factual) and writing free text, with a live preview and a reference number. GAP Two promises made in the UI copy are not backed by code: a stated "three working days to respond" service level has no backend enforcement, and a warning that fabricating a letter risks "referral to the relevant council" has no automated flagging, reporting or enforcement path behind it.

7.5 Mentor Events

An approved, active mentor can request to host a seminar, shadowing day, site visit or talk, giving a title, description, the concrete impact for learners, timing (at least 48 hours' notice), venue/province or an online flag, and a capacity. New events start hidden from learners and only appear once an administrator approves them. Registration is protected against overbooking with a database row lock on the very last seat. PARTIAL An "attended" field exists on each registration for post-event attendance tracking, but no feature was found that ever sets it — attendance marking is not yet built.

8. Administrator Functional Requirements

8.1 Admin sign-in & provisioning

There is no administrator self-registration. The very first administrator is created only by matching a configured bootstrap email against a verified sign-in, and only while no administrator yet exists — that path closes permanently afterwards. Every subsequent administrator is granted individually by an existing one.

8.2 Approvals queue

Three tabs: mentor/professional applications (with risk-flag indicators and partner-vetted badges), events (requiring a written reason of at least five characters to decline, and an urgency flag for events starting within a week), and administrators (Section 8.4). Every approval or rejection here is written to the audit log.

8.3 Analytics

CONFIRMED — the strongest evidence of this project's own honesty discipline. This screen was rebuilt after an earlier internal audit found several panels were entirely fabricated. Those panels (active-this-week usage, SMS-generated counts, offline-toggle rates, page views, and similar telemetry the platform never actually collected) were removed outright rather than backfilled with fake numbers. What remains today — total learners and province split, mean APS from real subject data, role counts, signup growth trends, mentor/application pipeline timing, device mix, and verification-tier mix — is backed by live database queries, and the screen states plainly, in its own text, that usage telemetry doesn't exist yet rather than pretending otherwise.

8.4 Team management & audit log

CONFIRMED An administrator can grant access to another account by email (with a required note) or revoke an existing administrator's access (with a required reason) — both write a full audit-log entry recording who did what, to whom, and why. Two safeguards are enforced server-side: an administrator cannot revoke their own access, and the last remaining active administrator cannot be revoked at all. The claim shown to every admin at sign-in — "every administrator action is recorded against your account in the audit log" — was independently verified true for every admin action examined (applications, events, admin grants/revokes) but was not exhaustively checked against literally every admin-surfaced action in the codebase.

9. Cross-Cutting Platform Features

9.1 Notifications

CONFIRMED Notifications are generated entirely server-side, as a direct consequence of real events — a new help request, a request being accepted or declined, a new message, a mentor event being approved or declined, or a learner confirming their own event registration — never invented client-side. They are read from and marked-read against the backend, with optimistic UI and automatic retry on failure.

9.2 Internationalisation

Six languages are supported for the main app interface: English, isiZulu, Setswana, Afrikaans, isiXhosa and Sesotho. The Advisor chat's language is deliberately independent of the app's display language, so a learner can read the interface in one language and converse with the advisor in another. PARTIAL A rough line-count comparison between the English and isiZulu translation tables shows a noticeable gap, suggesting the non-English languages may not have full key-for-key coverage; this should be confirmed with a direct translation-key diff before claiming full parity across all six languages.

9.3 Theming

Light, dark and system-follow themes, persisted locally and also saved to the learner's account so the choice follows them across devices. A live listener updates the app automatically if the device's own theme changes while in "system" mode.

9.4 Progressive Web App & offline behaviour

CONFIRMED The app is installable (native install prompt on Android/Chrome, guided manual instructions on iOS/Safari) and precaches its own application shell for offline use. API responses are deliberately excluded from that cache by design — the app has its own explicit, opt-in offline data strategy instead, specifically so a learner is never silently shown stale personal data by the service worker.

12. Known Limitations, Gaps & Recommendations

Presented here in one place for visibility, rather than only inline, so nothing is missed:

Account deletion is partial, not complete. "Delete my results" clears saved journey data only — the account, subjects, consent record and mentor-network history all remain. A genuine right-to-erasure endpoint does not yet exist.
The report-card OCR scanner is a simulation, openly labelled as such in-app, revealing pre-set example data rather than reading a real photo.
The "partner-vetted" mentor verification tier is unreachable through the self-service application flow as it stands, and no admin tool was found to grant it separately.
Two mentor-facing promises are copy-only: a stated three-working-day letter response time, and a stated consequence ("referral to the relevant council") for a fabricated recommendation letter. Neither is enforced in code.
Event attendance tracking is half-built. The data field exists; nothing in the product sets it.
PARTIAL Twilio SMS delivery for phone sign-in was being actively configured at the time of writing; South African carriers are known to filter unregistered sender numbers, so delivery should be confirmed with a real test message before relying on it.
PARTIAL Translation coverage across the five non-English languages has not been confirmed key-for-key against English; a direct diff is recommended before asserting full parity.
Documentation drift: this repository's own README.md backend section describes the API as substantially unbuilt and makes an incorrect claim about how authentication reaches Supabase. It should not be used as a reference for either topic until updated — this specification supersedes it for those purposes.
Backend hosting is not evidenced in the repository and should be confirmed directly against the actual hosting platform rather than assumed from any file here.
